## Repository layout

OPTEX is an eyewear retail platform for **Optex Opticians (Kenya)**. The binding contract is **OPTEX-SOW-2025-001-KE v3.0** (8-week Kenya build + a later Phase 3 Virtual Try-On) — see [docs/AUDIT.md](docs/AUDIT.md) and [docs/MISSING_FEATURES.md](docs/MISSING_FEATURES.md). The India v1 SOW is **superseded** (different payment stack — Razorpay/UPI vs M-Pesa/Pesapal/COD). The legacy `Frontend/` CRA+Vite mockup trees (visual reference only) have been **deleted from this repo** — they were a separate git repo, fully preserved on GitHub at `kalyan1421/Optex-frontend`, not referenced by any code here.

Repo siblings at the root:

- `apps/web/` — Next.js 14 customer storefront. Home, shop, PDP with JSON-LD, cart, checkout, order tracking, appointments, search, branch locator, login/signup. Server Components read Supabase **directly** for SSR/SEO pages; all writes go through `apps/api`. Customers upload a prescription from the profile page via `components/prescriptions/PrescriptionUpload.jsx` (added 2026-09-07, PR #14), which calls the API's upload endpoint in `apps/api/src/modules/prescriptions/` and mirrors its MIME-type and 10 MB limits client-side (the server re-checks both). The admin panel's `Prescriptions.tsx` reviews what a customer has uploaded but cannot upload on their behalf. The backend is covered by `apps/api/test/prescriptions.e2e-spec.ts`; the upload form itself has no Playwright spec yet.
- `apps/admin/` — Next.js 14 staff panel (renamed in spirit from "super-admin panel" — R1 made it multi-role). `(authed)` route group gated by `middleware.ts`, which checks two things server-side via the SSR cookie session: `app_metadata.role` is one of the 7 known staff roles (note: `app_metadata`, not `user_metadata` — the latter is user-writable and must never be trusted for authorization), and — for `super_admin` specifically — the session's `aal` claim is `aal2`, redirecting to `/mfa-challenge` otherwise. What a role can actually see/do beyond that is entirely data-driven: `lib/route-permissions.ts` maps each route to a permission, `lib/user-context.tsx`'s `UserProvider` fetches the caller's full permission set once from `GET /auth/me`, `AdminSidebar.tsx` filters nav items by it, and `PermissionGate` (wrapping the whole `(authed)` layout) blocks a direct page visit the role doesn't have. **16 pages** — the original 12 (dashboard, products, orders, customers, appointments, inventory, reviews, promotions, branches, analytics, payments, prescriptions), `staff` (CRUD + role/branch assignment) and `audit-log` (read-only, filterable) from R1, `eye-records` (the staff review queue for /eye-care intake, migration 0037), and `cancellations` (the branch-scoped cancellation-request queue, audit A-02) — plus `/mfa-setup` and `/mfa-challenge` outside the `(authed)` group, since a session that hasn't stepped up yet cannot pass through it.

## Local dev

Dev server ports (set in each app's `package.json` and mirrored in `.claude/launch.json`):

- `pnpm dev:api` → **`http://localhost:1111`** (NestJS, routes under `/api`, Swagger at `/api/docs`)
- `pnpm dev:web` → **`http://localhost:1112`**
- `pnpm dev:admin` → **`http://localhost:1113`**

(These were moved off 3000/3001/4000 to avoid collisions with other local processes — if you see those ports referenced in older docs/scripts, they're stale.)

Applying migrations to a **hosted** project is `Backend/supabase/migrate-hosted.sh` (reads `SUPABASE_DB_URL` from the environment, applies anything missing in order, records into `supabase_migrations.schema_migrations` so the dashboard and CLI agree; `--dry-run` to preview, `--seed` to also load demo data after an explicit confirmation). Deliberately separate from `docker/migrate.sh`, which targets the container by hostname and tracks in its own `_docker.migrations` — pointing that at a hosted database records state somewhere Supabase's own tooling cannot see.

Local Supabase stack: `docker compose up -d supabase-kong` brings up Postgres + Auth + REST + Storage + Kong (gateway at `:54321`, Postgres at `:54322`). `docker/migrate.sh` idempotently applies `Backend/supabase/migrations/*.sql` + `seed.sql` on every `supabase-migrate` run. Each app's `.env.example` ships working local-dev defaults (Kong URL, anon/service-role JWTs signed with the shared local JWT secret) — copy to `.env`/`.env.local` to run against the Docker stack.

## Backend (Supabase)

Schema, RLS, and Storage buckets live in `Backend/supabase/migrations/` (`0001_init_schema.sql` → `0044_push_devices.sql`) with dev seed in `Backend/supabase/seed.sql`. Notable later migrations: `0006_security_fixes.sql` (RLS lockdown on `orders` INSERT, `current_customer_id()` SECURITY DEFINER, `order_number` default, NOT NULL customer_id columns), `0007_security_meta.sql` (redefines `is_super_admin()` to check **`app_metadata.role`** only — the original `0001` version incorrectly checked `user_metadata.role`), `0008_api_hardening.sql` (atomic `place_order` RPC, promo-code column, `increment_promo_uses`, appointment reminder flags).

Migrations from the audit remediation (2026-08-15):

- `0020_checkout_stock_enforcement.sql` — **F-02**. `place_order` now locks the cart's `inventory` rows, rejects the checkout if any line exceeds available stock, and deducts across active branches, all inside the existing transaction. Before this, checkout never consulted inventory at all and every product was infinitely purchasable. Availability is the sum across branches because orders carry no fulfilment branch; a trigger gives new products zero-stock rows so they are visible in the admin grid rather than silently unsellable.
- `0021_cron_advisory_lock.sql` — **F-05**. `try_claim_cron_run` gives the scheduled jobs leader election with a lease, so the API can run more than one replica. Deliberately a transaction-scoped advisory lock over a lease row, not a session lock: session locks are unsafe over PostgREST's connection pool.
- `0022_reminder_flag_claim.sql` — **F-04**. `claim_due_reminders` selects, flags and returns due appointments in one statement, making reminder SMS exactly-once. The `reminder_24h_sent` / `reminder_1h_sent` columns 0008 added had never been wired up.
- `0023_notification_log.sql` — **F-06**. Durable record of every SMS/email attempt, with backoff and a retry sweep. Failures used to be logged to stdout and dropped.
- `0024_review_trust_and_ratings.sql` — **F-11, F-12**. `verified_purchase` on reviews (set once by trigger), plus trigger-maintained `rating_avg` / `rating_count` on `products` so listings can show stars without a per-product round trip.
- `0025_rbac_foundation.sql` — **CR-01 R1**. Five new tables — `roles`, `permissions`, `role_permissions` (the matrix, editable as data — granting a role a permission is an `UPDATE`, not a deploy), `staff_users` (the directory; mirrors `customers`' `deactivated_at` soft-deactivation pattern), `audit_log` (append-only, denormalizes the actor's role/branch _at the time of the action_). All RLS-enabled with zero policies (service-role only) — `apps/admin` never queries Postgres directly, so real enforcement lives in the API's `PermissionsGuard`, matching migration 0009's "RLS is defense-in-depth" philosophy. Seeds the 7 roles, 25 permissions, and the full role→permission matrix; backfills a `staff_users` row for every pre-existing `super_admin`.

- `0037_eye_records.sql` — structured home for the `/eye-care` intake form. Before it, the form's demographics, health-history checklist and self-reported prescription (SPH/CYL/AXIS/ADD/PD **per eye**) were flattened into `appointments.notes`, a 1000-char free-text column — nothing queryable or reportable. Deliberately NOT folded into `prescriptions` (0001): that table is the _upload_ pipeline (private-bucket `file_url`, signed-URL downloads, a pending→processed review queue the admin panel drives), so fileless self-reported rows would sit in that queue with nothing to download; it also has a single `pd` and no ADD columns. Adds `eye_records.read`/`.write` to 0025's matrix (branch_staff read, branch_manager read+write, super_admin both). Left off the `doctor` role on purpose — 0025 holds it at zero permissions until R5 ships, and this migration does not reopen that decision.

- `0038_eye_records_branch_scope.sql` — branch-scopes the 0037 review queue by denormalizing `branch_id` onto the record, stamped server-side from the linked appointment at insert. Deliberately not a query-time join through `appointment_id`: that column is ON DELETE SET NULL (so cancelling a visit does not destroy the clinical record), and a branch derived from it would vanish with the appointment, silently dropping the record out of every branch queue. A record with no appointment carries no branch and is visible only to an unscoped Super Admin.
- `0042_payment_attempt_guard.sql` — SPEC-11 **B-7**. Nothing used to bound concurrent payment attempts on one order, so two approved STK prompts debited a customer twice (the order was credited once; the surplus sat matched-but-unapplied for admin reconcile). `claim_payment_attempt(order, window)` reserves the order **before** the provider call — the pending row is only written after the provider answers, so a check-then-insert lets simultaneous requests both pass — under a transaction-scoped advisory lock (same reasoning as 0021). It reads the claim, then recorded `pending` rows on either rail; that order is load-bearing (the API records the row and _then_ releases). `PaymentsService` answers a repeat request to the same number with the live `CheckoutRequestID`, refuses a different number or the other rail with a 409, and releases only after recording — or after a plain provider refusal, but **not** when the outcome is unknown (a timed-out push may already be on the handset). Provider `fetch` calls gained explicit timeouts so a request cannot outlive its claim. If the function is missing (API deployed before the migration) payments proceed unguarded and log an error; any other claim failure fails closed. Covered by `payment-attempt-guard.e2e-spec.ts` (real concurrent HTTP requests) plus two unit specs.
- `0043_order_source.sql` — SPEC-11 **B-2**. `orders.source` (`web` | `ios` | `android`, CHECK-constrained) so the mobile goal "≥35% of online orders placed in-app" is measurable. The API derives it from the `X-Optex-Client` header (`common/client-info.ts`) and stamps it right after `place_order` commits — deliberately not folded into `place_order`, the most critical function in the system — and only for a mobile channel, so the storefront's checkout path is unchanged. `web` is the column default and means "not identified as a mobile app", not "proven to be the storefront": the storefront has never sent the header, so history and any client that omits or garbles it is correctly `web` with no backfill. Attribution, not authorisation — the header is client-supplied and nothing decides on it. The same parser feeds first-class `client` / `clientVersion` fields on every request log line (SPEC-11 §9). A failed stamp is logged and leaves the safe default rather than failing an order that has already been placed.
- `0044_push_devices.sql` — SPEC-11 **B-1**, push notifications. `device_tokens` (one row per handset; `token` is unique, so registering an existing token **moves** it to the caller — the shared-handset case — and per-device `muted_categories` is honoured at send time, server-side) and `'push'` on `notification_channel`, so push attempts sit in `notification_log` beside SMS and email (that is what makes "share of reminders delivered by push" measurable). `modules/push` adds `POST /devices` and `POST /devices/deregister` (token in the body, never the URL, so it stays out of access logs), an `FcmService` on the HTTP v1 API using a service-account JWT and `fetch` — no `firebase-admin`, the same approach as Daraja — and `PushService`, which `CustomerNotificationsService.notify()` calls at the one point every order, appointment and offer event already passes through. **Push is an optimisation over SMS, not a replacement**: SMS still goes out unconditionally, so a missed push loses nothing; letting push suppress it is SPEC-11 Q6 and needs the delivery data this now produces. Only `UNREGISTERED` or a sender mismatch ever disables a token — never a 400, a timeout or a quota error, which would let one bad deploy switch off the fleet — and push rows go to `notification_log` in a _terminal_ status so the retry sweep, which would re-send them as **email**, can never claim one. Off unless `FCM_SERVICE_ACCOUNT_JSON` is set; see the B-1 note in SPEC-11 for enabling it.

Auth model: Supabase Auth for both customers and staff. **CR-01 R1 replaced the single `super_admin` role with 7** — Super Admin, Branch Manager, Branch Staff, Inventory Manager, Accountant, Marketing, Doctor (the last currently holds zero permissions; reserved for the not-yet-built consultation module, R5). A staff member's role (and, for the two branch-scoped roles, their branch) lives in `app_metadata.role` / `app_metadata.branch_id` — server-set only, via the Admin API (**not** `user_metadata`, which any authenticated user can rewrite via the client SDK; this was a fixed self-escalation path, see below). What a role can actually do is looked up from `role_permissions` (data, not code) by `apps/api/src/auth/permissions.guard.ts`'s `PermissionsGuard`, which replaced the old hardcoded `RolesGuard`/`@Roles('super_admin')` across every admin controller. Three branch-scoped surfaces (appointments, inventory, orders) derive their filter from the caller's JWT `branch_id`, never a client-supplied one. Super Admin additionally requires **`aal2`** (TOTP 2FA, enforced both in `apps/admin/middleware.ts` and, decisively, in `PermissionsGuard` itself) — a valid-but-unverified super_admin token cannot reach a privileged route directly. Every mutation across 12 modules writes an `audit_log` entry via `AuditLogService.record()`, viewable (read-only) at `/audit-log` in the admin panel. `is_super_admin()` (SQL, RLS) still checks `app_metadata.role` only, unchanged since 0007. (The `user_metadata` self-escalation path was fixed and confirmed closed 2026-07-22, predating R1 — a signed-up customer could once call `auth.updateUser({ data: { role: 'super_admin' } })` and have the then-guard trust the resulting `user_metadata.role`.)

Branch-scoped surfaces are now **six**: inventory, appointments, orders, customers, cancellation requests (audit A-02 — `listForAdmin`, the pending-count badge, and `approve`/`decline` via `loadPendingRequest`, all scoped through the order's branch with an `!inner` join) and eye records (migration 0038). All six derive the filter from the caller's JWT `branch_id` and 404 rather than 403 on an out-of-branch id, so a response never confirms that another branch's row exists. `branch-scoping.e2e-spec.ts` covers all six, 20 tests.

`orders.branch_id` is populated as of **`0039_orders_fulfilling_branch.sql`**. It had existed unwritten since 0001, so the three order-derived scopes filtered on a permanently NULL column and a branch-scoped caller saw **no orders and no cancellation requests at all** — correct scoping code reading absent data. 0020 had declined to "invent a branch allocation the business has not asked for", which was right at the time; what changed is that 0026's `stock_ledger` records `('sold', from_branch_id, 'order_item', order_item_id)` per unit, so the fulfilling branch became a fact already in the data rather than a policy question. `place_order` now stamps it after deduction via `order_fulfilling_branch()`, and the migration backfills history. The one judgement call: a split order is attributed to the branch that supplied the **most** units (ties by branch id), so the minority branch does not see it — modelling every contributor would need a join table and a rewrite of all three call sites. Cancellation does not clear the stamp; restocking appends `sale_reversed` and leaves the `sold` rows, so a cancelled order stays visible to the branch that shipped it.

Payment webhooks (M-Pesa Daraja, Pesapal IPN) use the service-role key to bypass RLS and write to `mpesa_transactions` / `pesapal_transactions`. Prescription files are namespaced by customer id under the private `prescriptions` bucket; downloads are ownership-checked server-side (`prescriptions.service.ts`) before issuing a 60s signed URL.

## Deployment

Both tiers deploy on every merge to `main`; the `production` GitHub environment has **no approval gate**, so a merge ships straight to production.

- **Backend** (`apps/api`) → **Render**, at `https://optex-api.onrender.com`. `.github/workflows/cd.yml` re-runs the full CI suite as a `verify` gate, builds `apps/api/Dockerfile`, pushes to GHCR, then POSTs the `DEPLOY_WEBHOOK_URL` secret, which is what makes Render pull the new image. Only `api` is in the build matrix — `web`/`admin` keep working Dockerfiles but are deployed by Vercel, so building images for them would mean two pipelines shipping the same apps.
- **Frontend** (`apps/web`, `apps/admin`) → **Vercel**, built from `main` directly (projects linked in `.vercel/repo.json`). Both carry **Deployment Protection**, so their `*.vercel.app` URLs serve a Vercel login wall to anonymous requests — you cannot curl a deployed page to verify it; sign in first.
- The custom domains that appear throughout `docs/` (`optexopticians.co.ke`, `optex.co.ke`, `api.optexopticians.co.ke`) **do not resolve**. They are aspirational. The Vercel URLs and the Render URL above are the only live endpoints.

Configured since 2026-09-07: secret `DEPLOY_WEBHOOK_URL`; variables `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (variables, not secrets — the anon key is public by design; the service-role key must never appear there).

## Cross-cutting

- **CI** is wired up in `.github/workflows/ci.yml` — four jobs: `static` (typecheck, lint, build, Prettier check), `e2e` (API suite against a real Supabase stack), `smoke` (storefront Playwright against a production build) and `admin-e2e` (admin panel Playwright against a production build). The admin suite was local-only until then, which is how it came to depend on a Supabase URL that no longer matched the API's; `global-setup.ts` now fails fast with an explanation instead of timing out.
