## Repository layout

OPTEX is an eyewear retail platform for **Optex Opticians (Kenya)**. The binding contract is **OPTEX-SOW-2025-001-KE v3.0** (8-week Kenya build + a later Phase 3 Virtual Try-On) — see [docs/AUDIT.md](docs/AUDIT.md) and [docs/MISSING_FEATURES.md](docs/MISSING_FEATURES.md). The India v1 SOW is **superseded** (different payment stack — Razorpay/UPI vs M-Pesa/Pesapal/COD). The legacy `Frontend/` CRA+Vite mockup trees (visual reference only) have been **deleted from this repo** — they were a separate git repo, fully preserved on GitHub at `kalyan1421/Optex-frontend`, not referenced by any code here.

Repo siblings at the root:

- `apps/web/` — Next.js 14 customer storefront. Home, shop, PDP with JSON-LD, cart, checkout, order tracking, appointments, search, branch locator, login/signup. Server Components read Supabase **directly** for SSR/SEO pages; all writes go through `apps/api`. **Known gap:** the API's full prescription upload/list/download surface (`apps/api/src/modules/prescriptions/`) has no browser entry point anywhere in the storefront — no upload form on the profile page, in checkout, or elsewhere — and the admin panel's `Prescriptions.tsx` can only review what a customer has already uploaded, not upload on their behalf. The backend is thoroughly tested (`apps/api/test/prescriptions.e2e-spec.ts`); there is simply no UI that calls it. Found while closing audit F-17 (missing e2e coverage) — this is a missing feature, not a missing test, so it was flagged rather than built.
- `apps/admin/` — Next.js 14 staff panel (renamed in spirit from "super-admin panel" — R1 made it multi-role). `(authed)` route group gated by `middleware.ts`, which checks two things server-side via the SSR cookie session: `app_metadata.role` is one of the 7 known staff roles (note: `app_metadata`, not `user_metadata` — the latter is user-writable and must never be trusted for authorization), and — for `super_admin` specifically — the session's `aal` claim is `aal2`, redirecting to `/mfa-challenge` otherwise. What a role can actually see/do beyond that is entirely data-driven: `lib/route-permissions.ts` maps each route to a permission, `lib/user-context.tsx`'s `UserProvider` fetches the caller's full permission set once from `GET /auth/me`, `AdminSidebar.tsx` filters nav items by it, and `PermissionGate` (wrapping the whole `(authed)` layout) blocks a direct page visit the role doesn't have. **14 pages** — the original 12 (dashboard, products, orders, customers, appointments, inventory, reviews, promotions, branches, analytics, payments, prescriptions) plus `staff` (CRUD + role/branch assignment) and `audit-log` (read-only, filterable) from R1 — plus `/mfa-setup` and `/mfa-challenge` outside the `(authed)` group, since a session that hasn't stepped up yet cannot pass through it.
- `apps/api/` — NestJS backend (Node/Express under the hood). Owns all writes, payments, webhooks, comms, admin mutations, and cron jobs; will also serve the future Flutter app. Uses the Supabase **service-role client** (bypasses RLS; RLS stays as defense-in-depth). 16 feature modules: auth, catalog, cart, orders/checkout, payments (M-Pesa Daraja + Pesapal), notifications (Africa's Talking SMS + Resend email), appointments, prescriptions, reviews, promotions, branches, admin-metrics, cron, plus R1's **permissions** (role_permissions lookup, 60s-cached), **staff** (the staff directory + `app_metadata` sync), and **audit-log** (append-only privileged-action log). `pnpm -r typecheck` passes clean; no TODO/stub markers found in `src/`.
- `packages/ui/` — shadcn primitives (Button, Card, Input, Label, Badge, Separator) + `cn` + `formatKes` (NaN/null-safe), shared by web and admin.
- `packages/db/` — Hand-derived Supabase types, browser/server/service client factories, query helpers for the Next.js-direct-read paths. **Service client throws if imported on the client.**
- `packages/api-client/` — Typed client for `apps/web`/`apps/admin` to call `apps/api`.
- `packages/validators/` — Shared zod (or similar) validation schemas.
- `packages/config/` — Tailwind preset with brand tokens (`brand.blue #2A3182`, `brand.red #E53935`, `brand.dark #1A1A2E`) + Montserrat font + CSS-variable theme tokens.
- `Backend/supabase/` — Schema, RLS, storage migrations (`0001` through `0008`), seed. See [Backend/README.md](Backend/README.md).
- `docker-compose.yml` + `docker/` — Full local dev stack (Supabase Postgres/Auth/REST/Storage/Kong + the API), see "Local dev" below.
- `docs/AUDIT.md` — Consolidated tech-debt audit, Figma-to-code comparison, 8-week ship plan.
- `docs/MISSING_FEATURES.md` — Feature-by-feature gap analysis against the SOW + CR-01, refreshed 2026-07-22.

Local Supabase stack: `docker compose up -d supabase-kong` brings up Postgres + Auth + REST + Storage + Kong (gateway at `:54321`, Postgres at `:54322`). `docker/migrate.sh` idempotently applies `Backend/supabase/migrations/*.sql` + `seed.sql` on every `supabase-migrate` run. Each app's `.env.example` ships working local-dev defaults (Kong URL, anon/service-role JWTs signed with the shared local JWT secret) — copy to `.env`/`.env.local` to run against the Docker stack.

## Backend (Supabase)

Schema, RLS, and Storage buckets live in `Backend/supabase/migrations/` (`0001_init_schema.sql` → `0025_rbac_foundation.sql`) with dev seed in `Backend/supabase/seed.sql`. Notable later migrations: `0006_security_fixes.sql` (RLS lockdown on `orders` INSERT, `current_customer_id()` SECURITY DEFINER, `order_number` default, NOT NULL customer_id columns), `0007_security_meta.sql` (redefines `is_super_admin()` to check **`app_metadata.role`** only — the original `0001` version incorrectly checked `user_metadata.role`), `0008_api_hardening.sql` (atomic `place_order` RPC, promo-code column, `increment_promo_uses`, appointment reminder flags).

Migrations from the audit remediation (2026-08-15):

- `0020_checkout_stock_enforcement.sql` — **F-02**. `place_order` now locks the cart's `inventory` rows, rejects the checkout if any line exceeds available stock, and deducts across active branches, all inside the existing transaction. Before this, checkout never consulted inventory at all and every product was infinitely purchasable. Availability is the sum across branches because orders carry no fulfilment branch; a trigger gives new products zero-stock rows so they are visible in the admin grid rather than silently unsellable.
- `0021_cron_advisory_lock.sql` — **F-05**. `try_claim_cron_run` gives the scheduled jobs leader election with a lease, so the API can run more than one replica. Deliberately a transaction-scoped advisory lock over a lease row, not a session lock: session locks are unsafe over PostgREST's connection pool.
- `0022_reminder_flag_claim.sql` — **F-04**. `claim_due_reminders` selects, flags and returns due appointments in one statement, making reminder SMS exactly-once. The `reminder_24h_sent` / `reminder_1h_sent` columns 0008 added had never been wired up.
- `0023_notification_log.sql` — **F-06**. Durable record of every SMS/email attempt, with backoff and a retry sweep. Failures used to be logged to stdout and dropped.
- `0024_review_trust_and_ratings.sql` — **F-11, F-12**. `verified_purchase` on reviews (set once by trigger), plus trigger-maintained `rating_avg` / `rating_count` on `products` so listings can show stars without a per-product round trip.
- `0025_rbac_foundation.sql` — **CR-01 R1**. Five new tables — `roles`, `permissions`, `role_permissions` (the matrix, editable as data — granting a role a permission is an `UPDATE`, not a deploy), `staff_users` (the directory; mirrors `customers`' `deactivated_at` soft-deactivation pattern), `audit_log` (append-only, denormalizes the actor's role/branch *at the time of the action*). All RLS-enabled with zero policies (service-role only) — `apps/admin` never queries Postgres directly, so real enforcement lives in the API's `PermissionsGuard`, matching migration 0009's "RLS is defense-in-depth" philosophy. Seeds the 7 roles, 25 permissions, and the full role→permission matrix; backfills a `staff_users` row for every pre-existing `super_admin`.

Auth model: Supabase Auth for both customers and staff. **CR-01 R1 replaced the single `super_admin` role with 7** — Super Admin, Branch Manager, Branch Staff, Inventory Manager, Accountant, Marketing, Doctor (the last currently holds zero permissions; reserved for the not-yet-built consultation module, R5). A staff member's role (and, for the two branch-scoped roles, their branch) lives in `app_metadata.role` / `app_metadata.branch_id` — server-set only, via the Admin API (**not** `user_metadata`, which any authenticated user can rewrite via the client SDK; this was a fixed self-escalation path, see below). What a role can actually do is looked up from `role_permissions` (data, not code) by `apps/api/src/auth/permissions.guard.ts`'s `PermissionsGuard`, which replaced the old hardcoded `RolesGuard`/`@Roles('super_admin')` across every admin controller. Three branch-scoped surfaces (appointments, inventory, orders) derive their filter from the caller's JWT `branch_id`, never a client-supplied one. Super Admin additionally requires **`aal2`** (TOTP 2FA, enforced both in `apps/admin/middleware.ts` and, decisively, in `PermissionsGuard` itself) — a valid-but-unverified super_admin token cannot reach a privileged route directly. Every mutation across 12 modules writes an `audit_log` entry via `AuditLogService.record()`, viewable (read-only) at `/audit-log` in the admin panel. `is_super_admin()` (SQL, RLS) still checks `app_metadata.role` only, unchanged since 0007. (The `user_metadata` self-escalation path was fixed and confirmed closed 2026-07-22, predating R1 — a signed-up customer could once call `auth.updateUser({ data: { role: 'super_admin' } })` and have the then-guard trust the resulting `user_metadata.role`.)

**Known gap:** the cancellation-*request* admin workflow (`cancellation.service.ts`'s `listForAdmin`/`approve`/`decline`, reached via `/admin/cancellations*`) is not yet branch-scoped, unlike the rest of orders/appointments/inventory — a Branch Manager holding `cancellations.decide` can currently see and decide any branch's pending requests. Flagged during R1 1b rather than folded in; `order_cancellation_requests` needed its own design decision (it has no `branch_id` column, unlike `orders`).

Payment webhooks (M-Pesa Daraja, Pesapal IPN) use the service-role key to bypass RLS and write to `mpesa_transactions` / `pesapal_transactions`. Prescription files are namespaced by customer id under the private `prescriptions` bucket; downloads are ownership-checked server-side (`prescriptions.service.ts`) before issuing a 60s signed URL.

## Cross-cutting

- **CI** is wired up in `.github/workflows/ci.yml` — three jobs: `static` (typecheck, lint, build, Prettier check), `e2e` (API suite against a real Supabase stack) and `smoke` (storefront Playwright against a production build). **Not yet updated for R1**: no CI job runs the admin Playwright suite (it's local-only, always has been), and the `e2e` job doesn't need any change since R1's `MFA_ENFORCEMENT_ENABLED` override keeps the API suite's existing super_admin fixtures working unmodified.
- **Tests**: 183 API e2e tests across 20 suites (`apps/api/test/` — R1 added `rbac`, `branch-scoping`, `staff`, `audit-log`, and `mfa-enforcement`, the last proving the aal2 step-up with a real computed RFC 6238 TOTP code against the live GoTrue instance, not a stub), 25 storefront tests across 9 Playwright spec files (`apps/web/e2e/`; prescription upload/download has no browser entry point to test at all, see below) and 5 admin Playwright specs (`apps/admin/e2e/` — `global-setup.ts` now completes a real TOTP enrollment + challenge for its throwaway super_admin fixture rather than bypassing 2FA), plus 28 unit tests (`apps/api/test/unit/`, `packages/ui/src/lib/format.spec.ts` — audit F-08) covering the pure logic the e2e suite used to be the only way to reach. There are still **no contract tests** for `packages/api-client`, the typed boundary three apps depend on.
- **Load tests** live in `load/` (k6, audit F-07) and are not part of CI — they need a running stack. `load/README.md` explains why they target the storefront on :1112 rather than the API directly.
- `pnpm -r lint` works and is enforced in CI (ESLint + `jsx-a11y`; configs in `apps/web/.eslintrc.js` and `apps/admin/.eslintrc.js`).
- `pnpm -r typecheck` passes clean across all nine workspace projects, `apps/web` included.
- CR-01 Phase 1B: **R1 (RBAC) is done** — 7 roles, branch scoping, staff directory, audit log, Super Admin 2FA (`feature/rbac-r1`, not yet merged to `main`). R2 (inventory ledger), R3 (doctor consultation), R4 (product analytics), R5 (branch P&L) are **not started** and, per SPEC-08's build order, must follow R1 in that sequence — see `docs/MISSING_FEATURES.md` for the full breakdown (predates R1's completion, so its RBAC section is now stale).
